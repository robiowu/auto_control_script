# Feature Specification: 统一截图·输入·OCR 自动化平台

**Feature Branch**: `001-auto-control-platform`

**Created**: 2026-10-10

**Status**: Draft

**Input**: User description: "参考 game_deltaforce_factory 项目的 capture、interaction、ocr 模块，整合进 game_auto_control_script 并做本项目化重构。要求：1) 具备基本的截图识别功能，覆盖 Windows 各种方式与 ADB 安卓各种方式；2) 具备基本的操作输入功能，包含可后台与不可后台两类；3) 具备基本的 OCR 功能；4) 能作为类似按键精灵的工具脚本使用，并提供一套 UI 框架（可为 Web 页面），方便后续使用者快速以 CLI/工具函数方式调用上述能力，或通过网页快速构建自动化脚本（易用的自动化项目）。"

**Resolved Decisions**: 既有模块重构不向后兼容，旧接口直接替换（D1）；OCR 同时提供系统内置与高精度两类通道，默认自动选择（D2）；文档须教会使用者独立启用高精度通道（D3）。详见文末 Resolved Decisions。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 以工具函数/CLI 方式调用三大能力 (Priority: P1)

一名自动化脚本开发者希望在自写的 Python 脚本或命令行中直接调用"截图 / 输入 / OCR"三类能力，而不必关心 Windows 窗口句柄、ADB 命令行、图像格式转换等底层细节。他指定一个目标（Windows 窗口标题或安卓设备），即可拿到一张统一的截图对象；对该对象做 OCR 或模板匹配得到坐标；再对同一目标下发点击/输入动作。

**Why this priority**: 这是整个平台的能力底座，其他所有使用方式（Web 编排、按键精灵式脚本）都建立在它之上；不做这一层，后续场景无法独立交付价值。

**Independent Test**: 在一个 Windows 窗口（可被遮挡）上完成"后台截图 → OCR 识别出指定文字 → 按识别结果的坐标后台点击"，并在一台 ADB 设备上完成"截图 → 模板匹配 → 点击"，两次均无需把目标切到前台即可验证结果。

**Acceptance Scenarios**:

1. **Given** 目标窗口处于被其他窗口遮挡状态，**When** 调用截图能力并指定该窗口，**Then** 返回一张内容与窗口实际显示一致的图像，且窗口未被激活、未被置顶。
2. **Given** 已获取一张目标截图，**When** 对该图像做整图 OCR，**Then** 返回按阅读顺序排列的文字条目，每条包含文本内容、置信度与包围盒坐标。
3. **Given** OCR 返回了包含目标文字的条目，**When** 以该条目的包围盒中心为坐标对该目标下发点击，**Then** 目标在该位置收到一次点击，且坐标与图像所见位置一致。
4. **Given** 一台已通过 ADB 连接的安卓设备，**When** 依次调用截图、模板匹配、点击、文本输入，**Then** 各步骤均成功且坐标语义与 Windows 侧一致（均为相对目标左上角的逻辑坐标）。
5. **Given** 已安装本平台，**When** 在命令行中请求列出可用目标（Windows 窗口列表 / 安卓设备列表），**Then** 输出可直接作为后续命令参数的目标标识清单。

### User Story 2 - 通过网页界面可视化构建自动化脚本 (Priority: P1)

一名不熟悉代码的同事需要快速做出一段"打开界面 → 找到某个按钮 → 点击 → 等待 → 输入文字 → 校验结果"的自动化流程。他打开本地网页，从下拉框选择目标窗口或安卓设备，点击"预览"看到实时画面，在画面上框选区域或直接取点，把动作一步步添加到步骤列表，保存为脚本后点击"运行"，在下方的运行面板看到每一步的执行状态、日志与截图快照。

**Why this priority**: 用户明确要求"方便后续的人快速使用"，网页编排是降低使用门槛、让能力被非开发者复用的核心交付物。

**Independent Test**: 在网页中从零新建一段不少于 5 步的脚本（截图/找字/点击/输入/等待），保存后重新加载页面能再次打开该脚本，点击运行后能在运行面板逐步看到执行结果与截图快照，并可在任一步骤上单独试运行。

**Acceptance Scenarios**:

1. **Given** 网页已打开且本机存在多个可见窗口与至少一台已连接设备，**When** 打开目标选择器，**Then** 列出全部可选项并显示其分辨率/状态，选择后预览区显示该目标的实时画面。
2. **Given** 预览区已显示目标画面，**When** 在画面上拖拽框选一个区域或点击取一个点，**Then** 生成可直接填入步骤参数的区域/坐标值，且该值在后续步骤中可被引用来做点击或 OCR 区域识别。
3. **Given** 步骤列表中已有若干步骤，**When** 调整步骤顺序、修改参数或删除步骤，**Then** 列表即时更新，保存后脚本文件反映最新编排。
4. **Given** 已保存一段脚本，**When** 点击运行，**Then** 按步骤顺序执行，运行面板逐条输出每步的开始时间、结果、耗时与失败原因，并在每一步留下画面快照。
5. **Given** 脚本正在运行，**When** 点击暂停/继续/停止，**Then** 执行在最近一步边界处暂停、从暂停处继续、或立即终止并给出终止原因。
6. **Given** 某一步执行失败，**When** 查看运行面板，**Then** 能看到失败步骤的画面快照与可读的失败原因，且可单步重试该步骤。

### User Story 3 - 后台静默执行不打扰本机使用 (Priority: P2)

使用者希望在脚本运行期间继续用电脑做别的事，自动化过程不应抢夺鼠标键盘焦点、不应把目标窗口弹到最前、不应遮挡当前工作窗口。

**Why this priority**: 后台执行是"可后台输入"能力的核心价值，也是该能力区别于普通键鼠录制工具的卖点；但即便不做后台，前台模式仍可交付 Story 1/2，故此为 P2。

**Independent Test**: 启动一段循环点击脚本后，使用者在另一窗口持续输入文字，整个脚本运行期间输入焦点与鼠标位置不被抢走，脚本仍按预期完成全部点击。

**Acceptance Scenarios**:

1. **Given** 目标窗口处于遮挡或最小化状态，**When** 以后台方式执行点击与文本输入，**Then** 动作生效且前台窗口焦点与鼠标位置保持不变。
2. **Given** 目标应用不响应后台消息投递，**When** 使用者切换为前台输入方式执行同一步骤，**Then** 动作生效，且界面明确提示该方式会激活目标窗口。
3. **Given** 同一段脚本，**When** 使用者为每一步单独指定后台或前台方式，**Then** 按各步指定的方式执行，互不影响。

---

### User Story 4 - 多目标与安卓设备的自动化 (Priority: P2)

使用者需要同时对多个目标（多个 Windows 窗口、多台安卓设备、或两者混合）执行相同或不同的脚本，并能在界面上区分与管理这些目标。

**Why this priority**: 多设备是安卓自动化与多开场景的刚需，但单目标已能覆盖主要价值，故为 P2。

**Independent Test**: 同时连接两台安卓设备与选择一个窗口，为三者在网页中分别绑定不同脚本并并发运行，三者执行互不干扰，日志可按目标筛选查看。

**Acceptance Scenarios**:

1. **Given** 本机连接了多台安卓设备（含 USB 与网络方式连接的设备），**When** 列出设备目标，**Then** 每台设备以唯一标识列出并显示其连接状态与分辨率。
2. **Given** 脚本已绑定目标 A，**When** 使用者将脚本改绑到目标 B 并运行，**Then** 动作下发到 B，A 不受任何影响。
3. **Given** 多个目标正在并发执行，**When** 停止其中某一个，**Then** 仅该目标停止，其余继续执行。

---

### User Story 5 - 脚本沉淀、复用与移交 (Priority: P3)

团队希望把做好的自动化流程沉淀下来，交给下一个同事继续用或改造，避免每次从零开始。

**Why this priority**: 复用能放大前几个故事的价值，但依赖脚本能力先落地，故为 P3。

**Independent Test**: 导出一个已完成的脚本文件，在另一台装有本平台的机器上导入，选好目标后可直接运行并复现原有行为。

**Acceptance Scenarios**:

1. **Given** 一个已保存的脚本，**When** 使用者导出为文件并在另一环境中导入，**Then** 脚本的步骤、参数与区域定义完整保留。
2. **Given** 脚本中定义了基于固定分辨率的区域坐标，**When** 在分辨率不同的目标上运行，**Then** 系统按目标实际分辨率换算坐标并明确提示已换算，或在不支持换算时给出清晰报错。
3. **Given** 脚本中包含查找图片/文字的步骤，**When** 目标画面中不存在该图片/文字，**Then** 步骤按脚本设定的超时与失败策略处理，并记录一条可读的失败原因。

---

### Edge Cases

- 目标窗口在操作过程中被关闭、最小化到托盘、或标题发生变化：**如何发现并给出可读报错，而不是静默继续点向错误目标？**
- 安卓设备在运行中途掉线（USB 拔线/网络断开）或进入锁屏/息屏：**如何中断并告知，而不是把动作发往不存在的设备？**
- 目标分辨率、缩放比例、多显示器环境导致截图坐标与点击坐标不一致：**如何保证"看到哪里就点哪里"？**
- 目标画面尚未渲染完成（游戏加载中/画面全黑/纯色）：**如何避免把无效画面送去做识别并误判为"未找到"？**
- 中英文混合文本、竖排文本、艺术字、低对比度文字的 OCR：**识别为空或置信度过低时如何表达，而不是返回看似正常的错误结果？**
- 后台输入对某些应用不生效（应用只接受真实输入）：**如何明确暴露失败，而不是假装成功？**
- 网页界面在脚本运行期间被关闭或浏览器断连：**运行中的脚本如何处置，重启页面后能否看到历史运行记录？**
- 长时间运行产生的截图快照与日志堆积：**如何限制占用并可清理？**
- 同一目标被两个脚本同时操作：**如何避免动作互相穿插导致结果错乱？**
- 高精度 OCR 通道未安装、模型缺失或与既有依赖版本冲突：**如何保证平台仍可正常使用，并明确告知当前走的是哪条通道、缺失了什么？**
- 既有脚本在本次破坏性重构后未同步改造：**如何让使用者第一时间知道该换哪个新接口，而不是拿到一个含义不明的报错？**

## Requirements *(mandatory)*

### Functional Requirements

**目标与连接**

- **FR-001**: 系统 MUST 提供统一的目标抽象，使 Windows 窗口与安卓设备可以被同一套接口寻址、查询状态与释放。
- **FR-002**: 系统 MUST 能枚举本机可选的 Windows 窗口目标，输出可稳定复用的目标标识，并标明其可见性、分辨率与是否可用。
- **FR-003**: 系统 MUST 能枚举已连接的安卓设备目标（含 USB 直连与网络连接两类），标明设备标识、连接状态与分辨率。
- **FR-004**: 系统 MUST 在目标不可用（窗口关闭、设备掉线、句柄失效）时以可读错误中断当前操作，不得静默继续。

**截图能力**

- **FR-005**: 系统 MUST 支持对 Windows 目标截图，覆盖整屏、指定窗口、指定区域三种范围。
- **FR-006**: 系统 MUST 支持在 Windows 目标被遮挡或不在前台时仍能取到窗口内容，并支持在无法后台取图时明确报错而非返回黑图/空图。
- **FR-007**: 系统 MUST 提供多种 Windows 底层取图方式并可切换，在首选方式不可用时明确告知切换原因。
- **FR-008**: 系统 MUST 支持通过 ADB 对安卓设备截图，并支持多设备并发取图。
- **FR-009**: 系统 MUST 以统一的图像对象返回所有来源的截图，对象包含像素数据、尺寸、来源目标、采集时间与坐标系说明。
- **FR-010**: 系统 MUST 保证截图坐标系与实际下发坐标一致，涵盖系统缩放（DPI）、多显示器、窗口边框/标题栏差异等情形。
- **FR-011**: 系统 MUST 提供显式的资源释放接口，避免句柄、显存或设备连接泄漏；重复、高频取图时不得出现资源持续增长。

**输入能力**

- **FR-012**: 系统 MUST 支持后台输入方式：无需激活目标、不改变前台焦点与鼠标位置即可完成点击与文本输入。
- **FR-013**: 系统 MUST 支持前台输入方式：通过真实鼠标键盘完成动作，并在使用前明确提示会激活目标窗口。
- **FR-014**: 系统 MUST 支持以下动作：单击、双击、右键单击、移动、拖拽、滚轮、单键按下、组合键、文本输入。
- **FR-015**: 系统 MUST 支持中文等非 ASCII 文本的输入，且输入结果与目标应用接收到的一致。
- **FR-016**: 系统 MUST 支持通过 ADB 对安卓设备下发点击、滑动、长按、文本输入与按键动作。
- **FR-017**: 系统 MUST 让所有动作使用统一坐标语义（相对目标左上角的逻辑坐标），Windows 与安卓两侧保持一致。
- **FR-018**: 系统 MUST 允许为每个动作配置前置等待时长与随机抖动，并允许配置失败后的重试次数与间隔。
- **FR-019**: 系统 MUST 在动作目标不可用或动作未生效时以可读错误中断，不得吞掉失败继续下一步。

**OCR 与图像识别能力**

- **FR-020**: 系统 MUST 提供 OCR 能力：输入统一图像对象，返回按阅读顺序排列的文字条目，每条含文本内容、置信度与包围盒。
- **FR-021**: 系统 MUST 支持对图像的指定区域做 OCR，并返回相对原图的绝对坐标。
- **FR-022**: 系统 MUST 支持中英文识别，并允许指定识别语言。
- **FR-023**: 系统 MUST 同时提供系统内置引擎与高精度本地引擎两类 OCR 通道，默认自动选择：高精度引擎可用时优先使用，不可用时改用系统内置引擎，并在每次识别结果与界面上标明本次实际使用的引擎。
- **FR-024**: 系统 MUST 允许使用者显式指定使用哪一类 OCR 通道，覆盖默认的自动选择结果；被指定的通道前置条件缺失时，明确报错说明缺少什么。
- **FR-025**: 系统 MUST 提供从识别文本中提取结构化信息的能力（数字、金额、时间、百分比等），无法提取时明确返回空结果而非猜测值。
- **FR-026**: 系统 MUST 保留并纳入既有的模板匹配（找图）能力：输入图像与模板，返回命中位置与匹配置信度，未命中返回明确的不命中标识。
- **FR-027**: 系统 MUST 支持按文本查找与按图片查找两类定位方式，并返回可直接用于点击与区域识别的坐标。

**脚本编排能力**

- **FR-028**: 系统 MUST 支持以步骤序列表达一段自动化流程，至少覆盖：等待、截图、按图查找、按字查找、点击、输入文本、按键、拖拽、滚动、条件判断、循环、记录日志。
- **FR-029**: 系统 MUST 允许步骤引用前序步骤的定位结果作为坐标来源。
- **FR-030**: 系统 MUST 支持脚本的保存、加载、导入与导出，导出文件可在另一环境中还原全部步骤与参数。
- **FR-031**: 系统 MUST 支持运行控制：开始、暂停、继续、停止、单步执行与单步重试。
- **FR-032**: 系统 MUST 为每次运行记录逐步日志（步骤、结果、耗时、失败原因）与关键步骤的画面快照。
- **FR-033**: 系统 MUST 允许为查找类步骤设置超时与失败处理策略（超时继续、超时中止、重试）。
- **FR-034**: 系统 MUST 对运行产生的日志与快照设定保留上限并提供清理入口。

**Web 界面能力**

- **FR-035**: 系统 MUST 提供可在本地浏览器打开的网页界面，无需安装额外客户端即可使用。
- **FR-036**: 网页 MUST 提供目标选择器，列出 Windows 窗口与安卓设备并支持切换当前目标。
- **FR-037**: 网页 MUST 提供实时画面预览，并支持在预览画面上框选区域与取点，把结果直接填入步骤参数。
- **FR-038**: 网页 MUST 提供步骤编辑器，支持增删改与调整顺序，且编辑结果可保存为脚本。
- **FR-039**: 网页 MUST 提供脚本管理入口：新建、打开、保存、另存、导入、导出、删除。
- **FR-040**: 网页 MUST 提供运行控制台：实时展示每步状态、日志、画面快照，并支持开始/暂停/继续/停止与单步试运行。
- **FR-041**: 网页 MUST 在运行目标不可用、脚本参数非法、引擎缺失等情形给出界面可见且可读的错误提示。
- **FR-042**: 网页 MUST 支持在运行期间持续反馈进度，不得出现页面长时间无响应而无法得知执行状态的情况。

**CLI 与工具库能力**

- **FR-043**: 系统 MUST 提供命令行入口，可直接完成：列出目标、截图存文件、对图片或当前画面做 OCR 并输出文本、下发单次输入动作、运行脚本文件。
- **FR-044**: 命令行 MUST 支持机器可读的输出格式（如结构化文本）以便被其他脚本解析，并支持人类可读格式。
- **FR-045**: 系统 MUST 以库的形式暴露上述全部能力，使使用者在自己的脚本中直接导入调用，无需经由网页。
- **FR-046**: 系统 MUST 为所有对外能力提供说明其用途、参数与返回值的文档，且文档集中在项目统一入口中维护。

**工程与重构约束**

- **FR-047**: 整合进来的能力 MUST 遵循项目既有的模块与命名约定：**按能力分包组织**（截图、输入、OCR、查找、脚本编排各成一包，公共底座收敛到 `core/`），平台相关的能力包固定 `base.py` 抽象基类 + `factory.py` 工厂入口 + 平台实现文件；保持最小化的包初始化文件与完整路径导入。
- **FR-048**: 系统 MUST 在项目依赖清单中显式声明新增依赖，并保证安装脚本与依赖清单两处一致。
- **FR-049**: 系统 MUST 在运行日志中记录关键决策点（目标切换、取图方式切换、动作方式、本次实际使用的 OCR 通道与识别结果），便于事后定位问题。
- **FR-050**: 既有模块的重构 MUST 采用直接替换方式：旧的类名、函数名与签名直接改为新接口，不保留旧命名别名、不保留兼容层、不保留旧实现的回退分支；受影响的既有调用方在同一次变更中一并改造完成。
- **FR-051**: 系统 MUST 在项目统一说明文档中提供高精度 OCR 通道的启用指引，内容覆盖：安装步骤与依赖体积、模型获取方式、启用与切换方法、验证是否已生效的方法、常见失败（模型缺失、版本冲突、首次加载慢）的排查步骤；该指引 MUST 让从未接触过的使用者能独立完成启用。
- **FR-052**: 存在多种平台实现或多种通道的能力 MUST 由工厂统一分派：调用方通过 `create_*` 获取实现，由工厂按目标类型或通道选定具体实现，调用方不自行判断平台；显式指定的实现不可用时 MUST 报错说明原因，不回退到其它实现（与 FR-050 同源约束）。

### Key Entities

- **目标（Target）**: 一次自动化操作的载体，代表一个 Windows 窗口或一台安卓设备。关键属性：稳定标识、显示名称、类型、当前分辨率、可用状态、支持的取图与输入方式。
- **画面帧（Frame）**: 一次截图的结果。关键属性：像素数据、宽高、来源目标、采集时间、坐标系说明。所有识别与可视化都以此为单位。
- **识别结果（Match Result）**: 一次查找（按图或按字）的产物。关键属性：是否命中、文本内容（按字查找时）、置信度、包围盒或中心点坐标。
- **文字条目（Text Item）**: OCR 输出的最小单位。关键属性：文本内容、置信度、包围盒坐标、阅读顺序序号。
- **动作（Action）**: 一次输入操作。关键属性：动作类型、目标、坐标或文本、执行方式（后台/前台）、等待与重试配置。
- **脚本（Automation Script）**: 一段可保存、可复用的自动化流程。关键属性：名称、绑定的目标类型与基准分辨率、步骤序列、全局运行配置。
- **步骤（Step）**: 脚本的基本单元。关键属性：序号、步骤类型、参数（坐标/区域/文本/模板/超时/失败策略）、是否启用、备注。
- **运行会话（Run Session）**: 一次脚本执行过程。关键属性：脚本、目标、开始结束时间、整体状态、逐步执行记录、画面快照集合。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 新使用者从打开网页到成功跑通一段包含截图、找字、点击、输入、等待的 5 步脚本，耗时不超过 15 分钟，且全程无需阅读源码。
- **SC-002**: 在目标被遮挡的情况下，后台截图与后台点击的成功率达到 100%（在支持后台方式的目标应用上），且运行期间前台焦点与鼠标位置零次被抢占。
- **SC-003**: 同一段脚本在同一目标的连续 10 次运行中结果一致，坐标偏差为 0 像素，且不出现句柄/连接/内存泄漏导致的失败。
- **SC-004**: 对清晰的中文界面文字，OCR 在基准测试集上的单条文本识别准确率不低于 90%，且返回的包围盒中心点落在该文字区域内。
- **SC-005**: 单次截图到可使用的图像对象、单次 OCR 区域识别、单次输入动作，在常规界面分辨率下的耗时各自不超过使用者可感知的卡顿阈值（端到端单步不超过 3 秒，OCR 首次加载除外）。
- **SC-006**: 命令行与库调用两种方式对同一能力的返回结果语义一致，使用者从网页切到脚本编写时无需重新学习概念。
- **SC-007**: 运行日志与画面快照能让使用者在不复现问题的前提下，定位到失败发生在哪一步、当时的画面是什么、失败原因是什么，定位成功率不低于 90%。
- **SC-008**: 未接触过本项目的使用者，仅依据项目说明文档即可独立完成高精度 OCR 通道的安装、启用与生效验证，全过程无需额外咨询且一次成功。
- **SC-009**: 每次 OCR 调用的结果中都能明确看出本次使用的是哪一类通道；使用者按文档切换通道后，结果与日志中的通道标识随之改变。

## Assumptions

- 运行环境为 Windows 主机，安卓设备通过标准 ADB 通道接入，设备无需 root，仅使用系统允许的非侵入式通道。
- 网页界面定位为本机单机使用，默认仅监听本机回环地址，不引入账号体系与权限管理；如后续需要远程访问再单独评估。
- 自动化对象以桌面应用与游戏窗口为主，因此后台取图/输入是必选能力，而非可选项。
- 既有的项目模块（窗口句柄、Windows 截图找图、ADB 控制、日志、系统工具等）作为整合基础被复用与重构，不另起一套平行实现。
- OCR 同时提供系统内置通道（零安装、开箱即用、精度中等）与高精度本地通道（体积大、需获取模型、精度较高）；默认自动选择，高精度通道可用时优先，否则使用系统内置通道，使用者可显式覆盖。
- 高精度 OCR 通道为可选依赖：不安装时平台仍可完整使用（识别走系统内置通道），安装后自动被优先采用；其启用说明写入项目统一说明文档。
- 脚本默认以可视化步骤序列为表达形式，并可导出为可直接在命令行运行的脚本文件。
- 既有调用方不要求向后兼容：本次重构为一次性破坏性变更，旧接口直接替换，既有脚本在同一次变更中同步改造；如后续发现仍有遗漏的旧调用方，按同一策略继续替换而非补兼容层。
- 参考项目 `game_deltaforce_factory` 的 capture / interaction / ocr 模块作为实现参照来源，其面向单一游戏窗口的硬编码坐标与业务耦合（交易行区域常量等）不随迁移带入。
- 项目既有编码规范（文件头与函数头注释、命名约定、禁止静默降级、失败即报错、文档集中维护）适用于本次全部新增与重构代码。

## Resolved Decisions

- **D1（范围）既有模块重构的兼容策略**: 采用直接替换，不向后兼容。旧的类名、函数名与签名直接改为新接口，不保留别名、兼容层或旧实现回退分支，既有调用方在同一次变更中一并改造（FR-050）。
- **D2（部署与精度）OCR 通道策略**: 系统内置通道与高精度本地通道同时提供，默认自动选择（高精度可用时优先），使用者可显式指定；高精度通道为可选依赖，不安装时平台仍完整可用（FR-023、FR-024）。
- **D3（文档）高精度通道的可学性**: 项目统一说明文档须给出完整的启用指引（安装、模型获取、启用切换、生效验证、常见失败排查），保证使用者可独立完成（FR-051、SC-008）。
